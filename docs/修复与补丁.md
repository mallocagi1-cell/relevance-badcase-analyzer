# 修复与补丁

这份文档回答三个问题：rba 能不能修坏例？补丁文件里每个字段是什么意思？验收结果怎么读？

内容全部来自代码：`src/rba/repair/interventions.py`、`src/rba/repair/evaluate.py`、`src/rba/pipeline.py`（`evaluate_patch`、`_scoped_patch`、`_decision_position_patch`、`_write_patches`、`_mark_recommended`）和 `src/rba/analysis/hypotheses.py`。

## 一句话回答

**能，但只能"试修"。** rba 会生成补丁（一个小 JSON），你用 `rba eval` 在坏例和对照集上测它修好多少、弄坏多少。

**补丁不会写进权重，也不会导出新模型。** 补丁只在 `rba eval` 这个进程里，通过 PyTorch hook（钩子，运行时插进前向计算的一小段代码）临时生效。进程一结束，模型就还是原样。线上模型不会因为你跑了 `rba eval` 而改变。想真正上线，见文末「怎么真正上线」。

## 先认识几个词

| 词 | 意思 |
| --- | --- |
| 补丁 | 一个 JSON 文件，描述"在模型的哪个位置、做什么改动"。 |
| 干预 | 补丁在推理时真正做的那个改动。 |
| 决策位置 | 最后一个非填充 token 的位置。模型在这里输出等级。 |
| 残差（hidden） | 每层之间传递的向量，形状 `[batch, 序列长度, hidden 维]`。 |
| `W_U` | 输出头 `lm_head` 的权重矩阵。`W_U[g]` 是等级 g 那个 token 的一行。 |
| logit 差 | `logit(原预测) − logit(金标)`。大于 0 说明模型偏向错答案。干预让它变小就是"往对的方向推"。 |
| 发现集 | 分析时用来挑补丁的坏例。 |
| 验收集（holdout） | 按 id 哈希留出、分析时完全没看过的坏例。只给 `rba eval` 用。 |
| 对照集 | `goodcases`，模型原本判对的样本。用来看补丁会不会把对的改错。 |
| 修复率 | 改前错的坏例里，改后变对的比例。 |
| 回退率 | 改前对的样本里，改后变错的比例。 |

## 补丁从哪里来

1. `rba analyze` 对每个混淆组（如 `3->0`）挑出可疑组件，并在抽样坏例上做"干预复核"：每个目标带一个同类随机对照和一个 identity 对照（系数 1.0，应当毫无变化）。
2. 每条假设得到一个状态（见下文「状态」）。
3. 只有被推荐的假设会写出补丁文件和 `rba eval` 命令（`pipeline._mark_recommended`）：
   * 状态为「消融有效」的假设，每组最多推荐前 2 条。
   * 如果一组里没有任何「消融有效」，就推荐排名最高、还带补丁、且状态不是「被复核否定」「先处理这个」的那一条，并标成 `exploratory: true`（探索性）。
   * `lm_head_blend`（读出行混合）只作诊断，**永远不会被推荐**。
4. 文件写到 `输出目录/patches/<组名>_h<序号>.json`。组名里的 `->` 会变成 `_to_`，例如 `3_to_0_h2.json`。序号是这条假设在本组列表里的排名。
5. `patches/.rba_patches.json` 记着本次写了哪些文件。下次分析只删除这个清单里的文件。**你自己放进 `patches/` 的文件不会被删。**

## 补丁方法一览

`method` 字段决定方法。代码支持下面 6 个值。

| method | 改什么 | 自动生成？ | 推荐用来修？ |
| --- | --- | --- | --- |
| `head_scale` | 某层若干注意力头的输出乘一个系数 | 是 | 是，主力方法 |
| `mlp_zero` | 某层 MLP 输出清零 | 是 | 一般不推荐（诊断性，破坏面大） |
| `steering` | 在某些层的残差上加一个方向向量 | 否，只能手写 | 可以试 |
| `lm_head_blend` | 把某等级的输出行向另一等级的行混合 | 是，但只作诊断 | 否 |
| `ablate_tokens` | 指定 token id 所在位置的输入向量清零 | 否，手写 | 诊断用 |
| `ablate_image` | 同上，自动换成图像 token id | 是，诊断用 | 否 |

### head_scale：缩放注意力头

**做什么。** 一层注意力的输出是 `o = W_o · [z_0; z_1; …; z_{H-1}] + b`，`z_h` 是第 h 个头的输出（长度 `head_dim`）。`head_scale` 把选中头的那一段乘以 `scale`：

`o' = Σ_h  factor_h · W_o[:, h段] · z_h + b`，其中选中的头 `factor_h = scale`，其余为 1。

* `scale: 0.0` = 把这些头整个关掉（消融）。
* `scale: 0.5` = 减半。
* `scale: 1.0` = 不变（这就是 identity 对照）。

"输出投影"对全注意力层是 `o_proj`，对 GatedDeltaNet 线性注意力层是 `out_proj`。代码要求投影输入维能被头数整除，否则报错"注意力输出没法按头切开"。

**什么时候用。** 报告说某个头"消融有效"，你想看把它关掉或调小能不能修好坏例、又不伤对照。这是最"小"的补丁：只动一层的几个头。

**字段：**

| 字段 | 类型 | 必填 | 默认 | 含义 |
| --- | --- | --- | --- | --- |
| `layer` | 整数 | 是 | — | 层号，从 0 开始。超出范围报错。 |
| `heads` | 整数列表 | 是 | — | 头号，从 0 开始。例如 `[0]`、`[3, 5]`。 |
| `scale` | 浮点 | 否 | `0.0` | 乘到这些头上的系数。 |
| `scope` | 字符串 | 否 | `all_positions` | 见下文「作用范围 scope」。 |

### mlp_zero：MLP 清零

**做什么。** 把第 `layer` 层 MLP 的输出换成全 0。也就是这一层不往残差里写 MLP 的那部分。

**什么时候用。** 归因指向某层 MLP。注意：MLP 清零在假设里标为 `diagnostic_only`（只作诊断），因为一次清空整块 MLP 往往伤到别的样本。可以拿来定位，不建议当最终修复。

| 字段 | 类型 | 必填 | 默认 | 含义 |
| --- | --- | --- | --- | --- |
| `layer` | 整数 | 是 | — | 层号。该层没有 `mlp` 子模块会报错。 |
| `scope` | 字符串 | 否 | `all_positions` | `decision` 时只清零决策位置那一行。 |

### steering：残差方向推动

**做什么。** 在指定层的输出残差上加一个向量：`h' = h + alpha · v`。

`v` 有两种来源：

* `vector_source: "lm_head_diff"`（默认）：`v = (W_U[to_grade] − W_U[from_grade]) / ‖W_U[to_grade] − W_U[from_grade]‖`，即"从错等级指向对等级"的单位方向。两行几乎相同（范数 < 1e-8）会报错。
* 其他任何值：直接用 `vector` 字段里你给的数（长度必须等于 hidden 维）。不会归一化。

**什么时候用。** 你已知道某类错误整体偏向某个等级，想在最后几层轻推一下。rba 不会自动生成它，需要手写。`alpha` 要自己扫（如 0.5、1、2、4），每个值跑一次 `rba eval`。

| 字段 | 类型 | 必填 | 默认 | 含义 |
| --- | --- | --- | --- | --- |
| `layers` | 整数列表 | 否 | — | 在哪些层的输出上加。 |
| `layer` | 整数 | 否 | 最后一层 | 没写 `layers` 时用它。两个都没写就用最后一层。 |
| `vector_source` | 字符串 | 否 | `lm_head_diff` | 见上。 |
| `from_grade` | 字符串 | `lm_head_diff` 时必填 | — | 错等级，例如 `"0"`。 |
| `to_grade` | 字符串 | `lm_head_diff` 时必填 | — | 对等级，例如 `"3"`。 |
| `vector` | 浮点列表 | 非 `lm_head_diff` 时必填 | — | 自定义方向。 |
| `alpha` | 浮点 | 否 | `1.0` | 步长。 |
| `scope` | 字符串 | 否 | `all_positions` | `decision` 时只加在决策位置。 |

注意一个代码细节：`scope: decision` 时会给 `layers` 里每一层都加；`all_positions` 时也是每一层都加。

### lm_head_blend：读出行混合（只作诊断）

**做什么。** 临时改输出头一行：`W_U[grade] ← (1 − alpha)·W_U[grade] + alpha·W_U[toward]`。退出时恢复原权重。

**为什么不推荐。** 这个改动在代数上必然缩小两行的差距，所以"有效"几乎是注定的，不能说明根因。报告把它标为「仅相关」，不给推荐命令。

**共享权重时会被拒绝。** 很多 2B 模型的 `lm_head` 和输入 embedding 共享同一块权重（`tie_word_embeddings`）。这时改输出行也会改掉这个 token 的输入表示。`rba eval` 会直接报错拒绝（`_preflight_patch`），分析阶段也跳过这类复核（状态「未执行」）。

| 字段 | 类型 | 必填 | 默认 | 含义 |
| --- | --- | --- | --- | --- |
| `grade` | 字符串 | 是 | — | 被改的那一行（通常是错预测等级）。 |
| `toward` | 字符串 | 是 | — | 往哪一行混（通常是金标）。`grade == toward` 时什么都不做。 |
| `alpha` | 浮点 | 否 | `0.5` | 混合比例。 |

### ablate_tokens / ablate_image：按 token 清零

**做什么。** 在第 0 层的输入上（即 embedding 之后、第一层之前），把 `input_ids` 等于 `token_ids` 中任意一个的位置，整行向量置 0。

`ablate_image` 是简写：没写 `token_ids` 时，程序自动换成 `ablate_tokens` 并填上模型的图像 token id（`image_token_id`）。报告写出的补丁里已经替你填好。

**什么时候用。** 想知道"把图像整个拿掉会怎样"。这是很粗的诊断，不是修复。

| 字段 | 类型 | 必填 | 默认 | 含义 |
| --- | --- | --- | --- | --- |
| `token_ids` | 整数列表 | `ablate_tokens` 必填 | — | 要清零的 token id。空列表会报错。 |

### 作用范围 scope

| 值 | 意思 | 哪些方法支持 |
| --- | --- | --- |
| `decision` | 只在决策位置那一个 token 上改 | `head_scale`、`mlp_zero`、`steering` |
| `all_positions` | 所有位置都改 | `head_scale`、`mlp_zero`、`steering` |
| `readout` | 只改输出头（自动报告，不用写） | `lm_head_blend` |
| `token_positions` | 指定 token 的位置（自动报告） | `ablate_tokens`、`ablate_image` |

规则：

* 补丁里没写 `scope` 时，`rba eval` 按 `all_positions` 处理。
* 分析阶段的复核都是在 `decision` 上做的，所以报告写出的已复核补丁都带 `"scope": "decision"`。
* 对不支持 `decision` 的方法写了 `decision`，程序会退回整体干预，并在 `eval.json` 里把真实用到的范围写进 `scope`（你写的写进 `requested_scope`）。
* 两种范围是不同的实验。分析复核用 `decision`，你就用 `decision` 去验收，结果才和报告对得上。

## 补丁文件里的其他字段

这些字段由 `_write_patches` 写入。大部分只是记录，`rba eval` 真正读取的标在"eval 是否使用"。

| 字段 | 含义 | eval 是否使用 |
| --- | --- | --- |
| `method` | 方法名，见上 | 是，必填 |
| `scope` | 作用范围 | 是 |
| `verified_on_sample` | `true`：这份补丁就是分析时在抽样坏例上真正跑过的那个干预（系数、范围都一样）。`false`：没跑过。 | 否 |
| `untested` | `verified_on_sample` 的反面。为 `true` 时，eval 结论末尾会加一句"属于未经复核的提议"。 | 是（只影响结论文字） |
| `proposal_patch` | 假设里给的"更温和"的提议（例如 `scale: 0.5`），和真正复核过的干预（`scale: 0.0`）不同时才出现。文件主体是复核过的那个。 | 否 |
| `proposal_note` | 对 `proposal_patch` 的说明文字 | 否 |
| `comment` | 假设标题，例如"L0.self_attn.h0 的最终读出贡献…" | 否 |
| `group` | 所属混淆组，例如 `"3->0"` | 否 |
| `status` | 写文件时这条假设的状态，见下文 | 否 |
| `exploratory` | `true`：这组没有任何「消融有效」，这条只是探索性推荐，结果不能当机制证据 | 否 |
| `tiny_seed` | 分析时的 `seed`。eval 会把 `cfg.seed` 改成它（影响内置小模型初始化和验收集划分） | 是 |
| `plant_error` | 分析时的 `plant_error`。eval 会照抄（只对内置小模型有意义） | 是 |
| `grades` | 分析时的等级列表。和当前配置不同就报错 | 是（校验） |
| `run_fingerprint` | 生成补丁那次分析的指纹。和 `--run` 目录的指纹不同时，eval 会加一条注意并把 `replay_valid` 设为 `false` | 是（校验） |
| `tied_lm_head` | 分析时 lm_head 是否和 embedding 共享 | 否（eval 自己重新检测） |

想想 `proposal_patch` 是怎么来的：假设阶段给头补丁默认提议 `scale: 0.5`（更温和）；复核阶段为了测"这个头有没有作用"，跑的是 `scale: 0.0`。两者不同时，文件以复核过的 `0.0` 为准，`0.5` 留在 `proposal_patch` 里供你参考。想试 `0.5`，按下一节手改。

## 一份完整的补丁示例

下面是 `runs/example/patches/0_to_2_h2.json` 的真实内容（demo 小模型生成）：

```json
{
  "method": "head_scale",
  "layer": 0,
  "heads": [0],
  "scale": 0.0,
  "scope": "decision",
  "verified_on_sample": true,
  "untested": false,
  "proposal_patch": {
    "method": "head_scale",
    "layer": 0,
    "heads": [0],
    "scale": 0.5,
    "scope": "decision"
  },
  "proposal_note": "假设里给的是更温和的提议（例如 scale 0.5）；这里验收的是抽样复核时真正用过的干预。",
  "comment": "L0.self_attn.h0 的最终读出贡献（正值支持原预测，负值支持金标）",
  "group": "0->2",
  "status": "证据不足",
  "exploratory": true,
  "tiny_seed": 0,
  "plant_error": true,
  "grades": ["-1", "0", "1", "2", "3"],
  "run_fingerprint": "99df4eed…",
  "tied_lm_head": false
}
```

读法：第 0 层第 0 个头，在决策位置关掉。分析时真的这样跑过（`verified_on_sample: true`），但这组复核样本不到 4 条，所以状态是「证据不足」，又因为这组没有「消融有效」，它是探索性推荐（`exploratory: true`）。

## 手写或手改补丁

1. **别直接改报告生成的文件。** 下次 `rba analyze` 会按清单覆盖它。复制一份到 `patches/` 里起个新名字，例如 `patches/my_3_to_0_half.json`。
2. 只保留 `method` 和该方法的字段就能跑。建议保留 `grades` 和 `run_fingerprint`，让 eval 帮你校验没用错目录。
3. 改系数后，把 `untested` 设成 `true`、`verified_on_sample` 设成 `false`，提醒自己这个系数没被复核过。（不改也能跑，只是结论里少那句提醒。）

最小可用的手写示例：

```json
{"method": "head_scale", "layer": 12, "heads": [3, 7], "scale": 0.5, "scope": "decision"}
```

```json
{"method": "mlp_zero", "layer": 20, "scope": "decision"}
```

```json
{"method": "steering", "layers": [26, 27], "from_grade": "0", "to_grade": "3", "alpha": 2.0, "scope": "decision"}
```

```json
{"method": "ablate_image"}
```

常见报错：

| 报错 | 原因 |
| --- | --- |
| 补丁里没有 method | JSON 缺 `method` |
| 不认识的补丁方法 | `method` 拼错 |
| 层号 N 超出范围 | `layer`/`layers` 越界 |
| 第 N 层没有头 [...] | 头号越界（从 0 开始） |
| 注意力输出没法按头切开 | 这层投影维不能按头整除，换层或换 steering |
| ablate_tokens 补丁没有 token_ids | 手写 `ablate_tokens` 时没给 id |
| 补丁是在 grades=… 下生成的 | 补丁和当前配置的等级不一致 |
| lm_head 和输入 embedding 共享权重 | 共享权重模型上用了 `lm_head_blend` |

## 运行 rba eval

推荐写法（完整回放那次分析的配置）：

```bash
rba eval --run runs/example --patch runs/example/patches/3_to_0_h3.json
```

* `--run` 读 `runs/example/config.used.json`，恢复模板、等级、解码协议、模块路径、dtype、seed 等全部配置。
* `--run` 不能和 `--config` 同时用。
* 不写 `--output-dir` 时，结果写到 `runs/example/eval/eval.json`。**同一目录再跑会覆盖它**；比较多个补丁时请每次给不同的 `--output-dir`。
* 也可以加 `--device`、`--batch-size`、`--decode-protocol` 等覆盖项，只覆盖你写了的字段。

不用 `--run` 的写法：`rba eval --ft 微调目录 --badcases bad.jsonl --goodcases good.jsonl --patch p.json`（`--base` 不写时等于 `--ft`），或 `rba eval --config rba.yaml --patch p.json`。这样不保证和分析时一致，不推荐。

eval 做的事：

1. 加载模型，检测 lm_head 是否共享权重，做补丁预检。
2. 检查 `run_fingerprint` 和文件身份。分析之后模型、坏例、对照或图片变过，会打印"这不是同一次实验的回放"，并设 `replay_valid: false`。
3. 若有验收集：验收集"改前/改后"各跑一遍，作为主结果；发现集另跑一遍作为"发现集复评"。若没有验收集：坏例全量作为"发现集复评"。
4. 对照集"改前/改后"各跑一遍。和验收集内容相同的对照样本会被剔除。
5. 写 `eval.json`，在终端打印结论。

## 读懂 eval 输出

终端输出的样子（数字是示意）：

```text
验收集：准确率 0.0% → 50.0%，修复率 50.0%（2/4），净正确数变化 2。
对照：准确率 100.0% → 75.0%，回退率 25.0%（1/4）。
```

`eval.json` 顶层字段：

| 字段 | 含义 |
| --- | --- |
| `patch` | 实际用的补丁（`ablate_image` 已被替换成 `ablate_tokens`） |
| `bad` | 坏例主结果块（验收集，或没有验收集时的发现集） |
| `bad_source` | `holdout`（验收集）或 `discovery`（发现集复评） |
| `discovery` | 有验收集时，发现集复评的结果块；否则 `null` |
| `good` | 对照集结果块；没给对照集时 `null` |
| `excluded` | 被剔除的样本及原因 |
| `tied_lm_head` | lm_head 是否与 embedding 共享 |
| `decode_protocol` | 本次解码协议 |
| `requested_scope` / `scope` | 补丁要求的范围 / 实际用到的范围 |
| `provenance_notes` | 来源告警（指纹不同、文件变过） |
| `replay_valid` | 没有来源告警时为 `true` |
| `conclusion` | 结论文字（见下） |

每个结果块（`bad`、`discovery`、`good`）里：

| 字段 | 含义 |
| --- | --- |
| `n` | 样本数 |
| `n_wrong_before` / `n_right_before` | 改前错 / 对的条数 |
| `n_fixed` | 改前错、改后对的条数 |
| `n_regressed` | 改前对、改后错的条数 |
| `fix_rate` | `n_fixed / n_wrong_before`；分母为 0 时 `null` |
| `regression_rate` | `n_regressed / n_right_before`；分母为 0 时 `null` |
| `fix_rate_ci` / `regression_rate_ci` | 95% Wilson 区间 `[下限, 上限]` |
| `net_correct_change` | `n_fixed − n_regressed`，这批样本上净多对了几条 |
| `accuracy_delta` | `net_correct_change / n` |
| `n_new_illegal` | 改前全词表 top 是等级词、改后不是的条数 |
| `n_invalid_before` / `n_invalid_after` | `free` 协议下判为非法输出的条数 |
| `before` / `after` | 改前 / 改后的准确率、MAE、合法输出率等 |
| `per_grade` | 按金标等级拆开的同样统计 |
| `per_attribute` | 按 `attributes` 里每个属性的每个取值拆开的同样统计。看补丁伤了哪类样本 |
| `interval_note` | 区间的前提说明 |

### Wilson 区间是什么

样本少时，"2/4 = 50%"非常不稳。Wilson 区间给出真实比例大概率落在的范围。例如 demo 里修复率 0/7，区间是 `[0, 0.354]`：真实修复率可能高达 35%。区间越宽，越不能下结论。

它假设样本相互独立。同一个 query 的多条样本不独立，挑了很多补丁再挑最好的也会高估。代码不做这些校正（见 `interval_note`）。

### 结论字符串

`conclusion` 由几段拼起来，按顺序：

| 片段 | 出现条件 |
| --- | --- |
| "补丁不是这次分析目录生成的（指纹不同）。""分析之后这些文件变过：…" | 有来源告警（放在最前面） |
| "坏例修复率 X%。" 或 "坏例修复率无定义（修改前没有错误样本）。" | 总是 |
| "没有对照集，回退风险未知。" / "对照集里没有原本判对的样本，回退率无定义。" / "对照回退率 Y%。" | 三选一 |
| "当前坏例集净正确数变化 +N。""当前对照集净正确数变化 −M。" | 有对应数据时 |
| "补丁新增 K 条非法输出，不要保留未经复核的补丁。" | 新增非法输出 > 0 |
| "两项条件率不能直接比较净收益；…" | 总是 |
| "这些坏例就是用来选补丁的发现集，没有独立验收集…" | `bad_source = discovery` |
| "验收集是按 id 哈希留出的 N 条，没有参与选补丁。" | `bad_source = holdout` |
| "注意：lm_head 与 embedding 共享权重…" | 共享权重且方法是 `lm_head_blend`（实际会先被拒绝） |
| "这个补丁的系数或作用范围和抽样复核时的干预不同，属于未经复核的提议。" | `untested: true` |

### 为什么修复率和回退率不能相减

两个比例的分母是不同人群。举例：线上 1% 是错例。补丁修复率 50%，回退率 1%。净效果 = 1%×50% − 99%×1% ≈ −0.49 个百分点，反而变差。所以要按线上错误占比加权，或者在一份有代表性的独立验收集上直接看准确率。

### 怎么判断一个补丁值得留

一个可操作的检查表（不是代码规则，是建议）：

1. `bad_source` 是 `holdout`。否则只是复评，不代表泛化。
2. `replay_valid` 是 `true`。
3. `n_new_illegal` 为 0。
4. 修复率区间下限明显大于 0，回退率区间上限低于你事先定的上限。
5. `per_attribute` 里没有某一类样本回退特别多。
6. 换一份没参与过任何挑选的数据再跑一次。

## 报告里的状态

由 `hypotheses._status` 和 `rank_hypotheses` 决定。阈值都是绝对值 `1e-4`，"效果"是干预后 logit 差的平均变化（负数 = 往对的方向推）。

| 状态 | 条件 | 会推荐吗 |
| --- | --- | --- |
| 消融有效 | 复核样本 ≥ 4；平均变化 < −1e-4；至少 60% 样本同向 | 会（每组前 2 条） |
| 仅相关 | 没做复核，或只是诊断性干预（如 lm_head 行混合） | 只在探索性兜底时 |
| 被复核否定 | 样本 ≥ 4；平均变化 > 1e-4；改善比例 ≤ 40% | 不会 |
| 消融无效果 | 样本 ≥ 4；平均变化绝对值 ≤ 1e-4 | 只在探索性兜底时 |
| 复核不稳定 | 以上都不满足（方向不一致） | 只在探索性兜底时 |
| 证据不足 | 复核样本 < 4；或 identity 对照逐例有非零/非有限变化；或最终读出重建不可靠 | 只在探索性兜底时；identity 失败或重建不可靠时补丁被清空，不会推荐 |
| 先处理这个 | 等级词概率质量 < 0.5 | 不会 |
| 未执行 | 复核被跳过（例如共享权重下的 lm_head 行编辑） | 不会 |

「消融有效」只说明这个干预在这几条样本上把 logit 差往对的方向推了，**不证明它是根因**，也不保证不伤别的样本。所以一定要跑 `rba eval` 看对照集。

## 怎么真正上线

### 现在的差距

| 环节 | 现在有没有 |
| --- | --- |
| 生成补丁 | 有 |
| 在验收集、对照集上量化修复和回退 | 有 |
| 把补丁写进权重、另存一份模型 | **没有** |
| 导出可部署的 checkpoint / 合并脚本 | **没有** |
| 线上推理框架（vLLM、TensorRT 等）里应用 hook | **没有** |

代码层面：`interventions.py` 全是 context manager（`with` 语句块）。进入时改 `forward` 或挂 hook，退出时恢复。`lm_head_blend` 会改权重，但退出时 `weight.copy_(backup)` 拷回去。没有任何代码调用 `save_pretrained`。

### 手动上线的办法

下面是可行的做法，**都需要你自己写代码和验证，rba 不会替你做**。

**1. `head_scale`、`scope: all_positions`：可以直接改权重。** 把输出投影权重里对应头的列乘以 `scale`，这和 hook 在数学上等价（bias 不动）：

```python
import torch
from transformers import AutoModelForImageTextToText

model = AutoModelForImageTextToText.from_pretrained("微调目录", dtype=torch.bfloat16)
layer = model.model.language_model.layers[12]
proj = layer.self_attn.o_proj            # 线性注意力层是 layer.linear_attn.out_proj
n_heads = 16                              # 按 config 填
head_dim = proj.weight.shape[1] // n_heads
with torch.no_grad():
    for h in [3, 7]:
        proj.weight[:, h*head_dim:(h+1)*head_dim] *= 0.5
model.save_pretrained("微调目录-patched")
```

存完后，用新目录当 `--ft` 跑一次不带补丁的 `rba analyze`，或者用你线上的评测，确认准确率和 `rba eval` 的"改后"一致。

**2. `mlp_zero`、`all_positions`：可以直接改权重。** 把该层 `mlp.down_proj.weight`（以及 bias，如果有）置 0。破坏面大，不建议。

**3. `scope: decision` 的补丁：不能直接改权重。** 它只在最后一个 token 上生效，权重是所有位置共享的。选项：
* 改用 `all_positions` 重新跑 `rba eval`。如果结果仍然好，就按 1 或 2 落到权重上。
* 或者在线上推理代码里自己写同样的 hook（参考 `pipeline._decision_position_patch`）。推理框架要支持自定义 hook。

**4. `steering`：不能改成权重。** 它是加一个常数向量。可以改成在对应层加一个 bias（如果该层的输出投影有 bias 并且你能改结构），或者在推理代码里加 hook。

**5. `lm_head_blend`：不要上线。** 只作诊断。共享权重的模型改它还会同时改输入 embedding。

**6. `ablate_tokens` / `ablate_image`：不要上线。** 等于让模型看不见图片。

### 更稳妥的长期路线

补丁说明了"哪里出了问题"。真正的修复通常是：针对这类坏例补数据、调整训练配方，或对可疑层做小范围再训练，然后用同一套 `rba eval` 对照集口径去验收新模型。
